## Importance 5

- **L30** (2026-07-27) Eine Trust-/Sicherheitsgrenze, die nur beim EINGANG geprueft wird, ist offen, sobald ein ZWEITER Pfad denselben Datenbestand spaeter erneut konsumiert. Konkret: wrap-up prueft trust_source=conversation beim Enqueue in user-candidates.json — die spaeter eingefuehrte Full-Queue-Re-Review (gebaut, damit Promotions nicht verhungern) las genau die Altbestaende, die nie durch diesen Check liefen, und konnte eine vergiftete Zeile nach identity/user.md promoten. Fix: die Grenze auf JEDEM Pfad erzwingen (Enqueue UND Promote) + Regressionstest mit einem Alt-Kandidaten ohne conversation-Provenance. Pruefmuster fuer jedes Gate: gibt es einen Re-Review-, Backfill- oder Migrations-Pfad, der Altbestand ohne dieselbe Pruefung anfasst?  #security #trust-boundary #identity #wrap-up #gate-design
- **L34** (2026-07-27) Prefix-Cache-Invalidierung ist der teuerste Einzelposten einer Agenten-Session, und sie wird von genau zwei Operationsklassen ausgeloest: solchen, die den ANFANG des Kontexts aendern. Gemessen ueber 7 Transkripte und ~1300 API-Calls, normalisiert auf Gelegenheiten: nach einem Skill-Aufruf folgt in 41% der Faelle ein voller Prefix-Rewrite (9/22), nach ToolSearch in 26% (5/19), nach Workflow 25% (1/4) — gegen Bash 0,5% (3/618) und Edit 0% (0/233). Grund: Skill laedt einen Body und ToolSearch aendert die Tool-Liste im System-Prompt, waehrend normale Tool-Calls hinten anhaengen und den Cache behalten. Ein Rewrite bei 100k+ Kontext kostet $1.20-$2.30 (cache_creation = 12,5x cache_read). Konsequenz: Skill-Delegationsketten und einzeln abgesetzte ToolSearch-Calls sind teure Architektur-Entscheidungen, keine neutralen Aufrufe — buendeln oder durch Skripte ersetzen. WICHTIG zur Methode: eine erste Auswertung PRO SESSION zeigte keinen Zusammenhang (eine Session mit 0 Skills hatte 5 Rewrites) — der Effekt wurde erst sichtbar, als auf Gelegenheiten normalisiert wurde statt auf Sessions.  #cost-analysis #prompt-cache #agent-design #skills #toolsearch #measurement
- **L11** (2026-06-03) Marker-basierte Drift-Tests (grep auf SKILL.md-Body) sind nur dann echte Tests, wenn man sie bidirektional gegenprueft: strip die Haertung -> Test MUSS rot werden, restore -> gruen. Mehrfach in dieser Session blieb ein Test faelschlich gruen nach dem Strip, weil seine grep-Alternation (`a|b|c`) noch von UNVERWANDTEM Text in derselben Datei getroffen wurde (z.B. trust-boundary-Test matchte 'NotebookLM' aus einem voellig anderen Step-7-Sync-Abschnitt; recency-Test matchte 'pause'/'runtime' aus Nachbarregeln). Codex-Verifier fand dieselbe Klasse als 3 MAJOR ('Test pinnt das Konzept, aber nicht jede Spec-Zusage'). Fix-Muster: (a) jeden Hebel mit einem EINDEUTIGEN Marker im Body verankern `(lever-N)`/`(trust-boundary)`/`(pattern-schema-canon)`, (b) den Test an diesen Marker UND eine konzept-spezifische Phrase binden, (c) bei datei-weiten Vorkommen den Marker-BLOCK isolieren (`grep -A2 marker`), nicht die ganze Datei greppen. Lehre: ein gruener marker-Test beweist nichts ohne die strip->FAIL-Gegenprobe.  #agentic-os #testing #drift-test #tdd #grep #verification #false-green #codex-review
- **L13** (2026-06-03) Plugin-Skill-Logik mit harten Invarianten (Privacy-Filter, Promotion-Gate, Decay-Floor, nie-Loeschen) gehoert in ein sourcebares Skript (scripts/global-schema.sh) mit ECHTEN Unit-Tests, NICHT nur in den SKILL.md-Prompt-Text. Begruendung (Hybrid-Architektur 4.A): Ein Prompt-beschriebener Mechanismus ist nur so verlaesslich wie der Agent, der ihn im Moment interpretiert — bei Daten-Integritaet/Datenschutz zu schwach. Eine Funktion is_denied(['api_key'])==denied ist bidirektional beweisbar (strip Deny-Array -> Leak -> Test FAILt); ein grep auf 'MEM_GLOBAL_DENY_TAGS im Prompt' beweist nichts (L11). Trennung: pure testbare Funktionen ins Skript, Orchestrierung/Entscheidung bleibt im Prompt (Skills SIND Prompts). Diese Session live demonstriert: beim manuellen Sync musste ich die Dedup/Provenance-Logik ohnehin ad-hoc in Python schreiben — also gleich getestet im Skript verankern.  #agentic-os #architecture #hybrid #testing #skill-vs-script #invariants #global-memory #tdd
- **L14** (2026-06-03) Eine Schema-Migration, die Bestands-Daten mit einem Default-Wert backfillt, muss die SPAETER eingefuehrte Validierungs-Regel SCHON beim Backfill anwenden — sonst erzeugt sie Eintraege, die die eigene Regel verletzen. 4.A: die Migration stempelte alle 44 Alt-Eintraege lifecycle:'active' (Default), aber das Promotion-Gate verlangt fuer 'active' |source_projects|>=2 -> 35 sofortige 'promotion-gate violations' (3 Patterns + alle 32 Learnings mit 1 Projekt). - **L1** (2026-04-30) Python's Default-Encoding unter Windows ist cp1252 — JSON-Dateien mit Umlauten oder UTF-8-Sonderzeichen werden faelschlich als korrupt markiert wenn man `open(path)` ohne `encoding='utf-8'` aufruft.
